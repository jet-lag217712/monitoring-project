# Backend API Architecture

## Purpose

The Backend API is the primary read interface for monitoring data stored in PostgreSQL.

It exposes UI/UX Cloud Plane data to frontend clients through REST-based API contracts and prevents database structure changes from leaking into dashboard functionality.

## Plane Ownership

Plane: UI/UX Cloud Plane.

The Backend API runs with the cloud services that own ingestion, PostgreSQL, visualization, aggregation, and monitoring state.

## Responsibilities

The Backend API is responsible for:

- Providing device inventory data.
- Providing site inventory data.
- Providing interface information.
- Providing metric history.
- Providing active and historical alerts.
- Enforcing API contracts.
- Translating database records into API responses.
- Enforcing application access controls.

The Backend API is not responsible for:

- SNMP polling.
- Telemetry transport processing.
- Data ingestion.
- Alert generation.
- Direct database administration.
- Device configuration or console access.

## Dependencies

Upstream:

- PostgreSQL Database.

Downstream consumers:

- UI/UX Cloud Plane frontend.

## Service Boundaries

The Backend API operates as a read-oriented application service for MVP monitoring workflows.

All monitoring data is generated by the Ingestion Service and persisted within PostgreSQL.

The Backend API does not write monitoring samples.

Future administrative functions may introduce write operations for:

- User management.
- Alert acknowledgement.
- Dashboard preferences.

These capabilities are outside the MVP scope.

## Data Flow

```text
Cloud Ingestion
    ↓
PostgreSQL
    ↓
Backend API
    ↓
UI/UX Cloud Plane
```

The Backend API is the only service expected to expose monitoring information to frontend consumers.

## API Design Principles

The API follows REST conventions.

Resources are exposed through predictable URL structures.

Responses use JSON.

All timestamps are returned in UTC using ISO-8601 format.

Example:

```text
2026-06-01T18:45:00Z
```

## Core Resources

### Sites

Represents monitored locations.

Examples:

```text
GET /api/sites
GET /api/sites/{siteId}
```

### Devices

Represents monitored network devices.

Examples:

```text
GET /api/devices
GET /api/devices/{deviceId}
GET /api/sites/{siteId}/devices
```

### Interfaces

Represents device interfaces discovered through IF-MIB.

Examples:

```text
GET /api/devices/{deviceId}/interfaces
GET /api/interfaces/{interfaceId}
```

### Metrics

Represents historical time-series data.

Examples:

```text
GET /api/devices/{deviceId}/metrics
GET /api/interfaces/{interfaceId}/metrics
```

Supported query parameters:

- `start`
- `end`
- `metric`

### Alerts

Represents monitoring events.

Examples:

```text
GET /api/alerts
GET /api/alerts/{alertId}
GET /api/devices/{deviceId}/alerts
```

## Error Handling

All API errors return a consistent structure.

Example:

```json
{
  "error": {
    "code": "RESOURCE_NOT_FOUND",
    "message": "Device not found"
  }
}
```

Common error codes:

- `RESOURCE_NOT_FOUND`
- `VALIDATION_ERROR`
- `INTERNAL_SERVER_ERROR`
- `DATABASE_ERROR`

## Authentication

Authentication is planned for the MVP and will use Google Single Sign-On through OpenID Connect, as requested by OGSD.

The frontend will authenticate users through Google, and the Backend API will validate issued identity tokens before granting access to protected resources.

Initial authorization requirements are expected to be minimal, with authenticated users granted access to monitoring data. More granular permissions may be introduced in future releases.

Future enhancements may include:

- Role-Based Access Control.
- Group-based authorization.
- Session management.
- Audit logging for user activity.
- Support for additional OpenID Connect identity providers.

## Logging

The service produces structured JSON logs.

All requests should include:

- Timestamp.
- HTTP method.
- Endpoint.
- Response status.
- Request duration.

Sensitive information must never be logged.

## Availability Requirements

The Backend API should remain stateless.

Multiple instances may be deployed behind a load balancer.

No application state should be stored locally.

## Future Enhancements

Potential future capabilities include:

- Authentication and authorization.
- WebSocket streaming.
- Alert acknowledgement endpoints.
- Dashboard user preferences.
- Audit logging.
- Multi-tenant support.

## Deployment Boundary

The Backend API runs in the UI/UX Cloud Plane.

Network access:

```text
Frontend
    ↓
Backend API
    ↓
PostgreSQL
```

Direct database access from frontend clients is prohibited.

All frontend interactions must occur through the Backend API.
