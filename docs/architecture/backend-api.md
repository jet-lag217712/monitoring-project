# Backend API Architecture

## Purpose

The Backend API serves as the primary read interface for the OGSD Monitoring Platform.

It exposes monitoring data stored within PostgreSQL to the Monitoring Dashboard through a REST-based API.

The Backend API acts as a boundary between the frontend and database layers, ensuring that database structure changes do not directly impact dashboard functionality.

---

## Responsibilities

The Backend API is responsible for:

* Providing device inventory data
* Providing site inventory data
* Providing interface information
* Providing metric history
* Providing active and historical alerts
* Enforcing API contracts
* Translating database records into API responses

The Backend API is not responsible for:

* SNMP polling
* MQTT processing
* Data ingestion
* Alert generation
* Direct database administration

---

## Dependencies

### Upstream Dependencies

* PostgreSQL Database

### Downstream Consumers

* Monitoring Dashboard

---

## Service Boundaries

The Backend API operates as a read-only service.

All monitoring data is generated by the Ingestion Service and persisted within PostgreSQL.

The Backend API does not write monitoring data.

Future administrative functions may introduce write operations for:

* User management
* Alert acknowledgement
* Dashboard preferences

These capabilities are outside the MVP scope.

---

## Data Flow
``` text
SNMP Collector
↓
MQTT Broker
↓
Ingestion Service
↓
PostgreSQL
↓
Backend API
↓
Monitoring Dashboard
```
The Backend API is the only service expected to expose monitoring information to external consumers.

---

## API Design Principles

The API follows REST conventions.

Resources are exposed through predictable URL structures.

Responses use JSON.

All timestamps are returned in UTC using ISO-8601 format.

Example:

2026-06-01T18:45:00Z

---

## Core Resources

### Sites

Represents monitored locations.

Example:

GET /api/v1/sites

GET /api/v1/sites/{siteId}

---

### Devices

Represents monitored network devices.

Example:

GET /api/v1/devices

GET /api/v1/devices/{deviceId}

GET /api/v1/sites/{siteId}/devices

---

### Interfaces

Represents device interfaces discovered through IF-MIB.

Example:

GET /api/v1/devices/{deviceId}/interfaces

GET /api/v1/interfaces/{interfaceId}

---

### Metrics

Represents historical time-series data.

Example:

GET /api/v1/devices/{deviceId}/metrics

GET /api/v1/interfaces/{interfaceId}/metrics

Supported query parameters:

* start
* end
* metric

---

### Alerts

Represents monitoring events.

Example:

GET /api/v1/alerts

GET /api/v1/alerts/{alertId}

GET /api/v1/devices/{deviceId}/alerts

---

## Error Handling

All API errors return a consistent structure.

Example:

{
"error": {
"code": "RESOURCE_NOT_FOUND",
"message": "Device not found"
}
}

Common error codes:

* RESOURCE_NOT_FOUND
* VALIDATION_ERROR
* INTERNAL_SERVER_ERROR
* DATABASE_ERROR

---

## Authentication

Authentication is planned for the MVP and will use Google Single Sign-On (SSO) through OpenID Connect (OIDC), as requested by OGSD.

The Monitoring Dashboard will authenticate users through Google, and the Backend API will validate issued identity tokens before granting access to protected resources.

Initial authorization requirements are expected to be minimal, with authenticated users granted access to monitoring data. More granular permissions may be introduced in future releases.

Future enhancements may include:
- Role-Based Access Control (RBAC)
- Group-based authorization
- Session management
- Audit logging for user activity
- Support for additional OIDC identity providers

---

## Logging

The service produces structured JSON logs.

All requests should include:

* Timestamp
* HTTP Method
* Endpoint
* Response Status
* Request Duration

Sensitive information must never be logged.

---

## Availability Requirements

The Backend API should remain stateless.

Multiple instances may be deployed behind a load balancer.

No application state should be stored locally.

---

## Future Enhancements

Potential future capabilities include:

* Authentication and authorization
* WebSocket streaming
* Alert acknowledgement endpoints
* Dashboard user preferences
* Audit logging
* Multi-tenant support

---

## Deployment Model


The Backend API runs as a Docker container within the AWS private subnet.

Network access:
```text
Monitoring Dashboard
↓
Backend API
↓
PostgreSQL
```
Direct database access from the frontend is prohibited.

All dashboard interactions must occur through the Backend API.
